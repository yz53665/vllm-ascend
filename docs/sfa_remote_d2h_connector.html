读懂 SfaRemoteD2HConnector
远端 KV 拉取式连接器

它把 Prefill 已经算好的 KV，不推、只通知：由 Decode 主动通过 MemFabric 从 Prefill 的 HBM 把主 KV 拉进自己托管的 CPU pinned 池，把 indexer KV 拉进本地 HBM，并逐层完成“读完了”的复用握手。

01

一句话定位：它是“拉”不是“推”

在 PD 分离部署里，Prefill 只负责算 prompt 的 KV；Decode 需要这段历史 KV 才能继续生成。 传统做法是 P 把 KV push 给 D。这个 connector 反过来：P 只登记自己的源地址并发送“这层写好了”的通知，D 自己去读。

P 侧

只暴露，不搬运

把本地 HBM 注册进 MemFabric，启动发送线程；每层 KV 写好后发 READ_READY_BATCH，等 D 回 READ_DONE 才允许复用该层物理 buffer。

D 侧

主动拉，自己决定落点

D 持有自己的 block 分配（主 KV 的 CPU block、indexer 的 HBM block），收到通知后按 TP 切分、合并连续区间，直接调用 MemFabric 批量读。

为什么

所有权决定方向

Decode 的 offload 管理器拥有 CPU 池，P 不可能知道 D 的 block 布局。让 D 拉，才能把“目的地解析”留在唯一知道答案的一侧。

“RD2H” 到底指什么

Remote Device to Host：远端设备（Prefill 的 NPU HBM）到本地主机内存（Decode 的 CPU 池）。但它不是单一目的地：

数据Prefill 源Decode 目的原因
主 MLA KV（K/V 两个张量）P 的 HBM 层缓冲SparseKVOffloadManager 的 TP 共享 CPU pinned 池Decode 的模型本就不在 HBM 保留完整主 KV，只保留稀疏热区
Indexer KV（DSA/lightning indexer）P 的 HBMD 每个 TP rank 的本地 HBMtop-k 选择每步都要用，必须常驻设备
Indexer scale（LIC8/int8 量化）P 的 HBMD 的 HBM，跟随 indexer反量化参数与 indexer 同生命周期
fused_copy_sfa 热区（tail / dense）P 的主 KV blockD 的每层 top-k 环形缓冲短请求或末尾不完整 block 直接 D2D，省一次 H2D
核心记忆点：主 KV 去 CPU，indexer/scale 去 HBM。方向是 D 拉 P，控制面是 ZMQ，数据面是 MemFabric。
02

使用场景与启用方法

适用于：PD 分离 + Decode 侧稀疏 KV offload（SFA / MLA + lightning indexer）。 Prefill 通常还会叠加 AscendStoreConnector 做逐层 offload，所以用 MultiConnector 组合。

启动前必须满足的约束

两侧配置互斥

  • P sparse_kv_offload_config.enabled 必须为 false（connector 构造时断言）。
  • D sparse_kv_offload_config.enabled 必须为 true（connector 构造时断言）。
  • 传输后端只能是 memfabric；缺失 transfer_backend 会直接抛错。

拓扑与端口

  • P 的 TP 必须 ≥ D 的 TP，且能整除（tp_ratio = P_tp / D_tp）。
  • 只有 D 绑定控制端口：基址 kv_port + dp_rank × tp_size，每个 TP rank 再 +tp_rank。
  • 因此 D 侧需要预留 dp_size × tp_size 个连续端口。
  • 稀疏 Decode offload 支持 DP + TP；CP / PP 组合不在支持范围。

请求是怎么被“路由”进来的

Proxy 在发给 Decode 的请求里写入 do_remote_prefill=true 与 metaserver 地址；Decode 侧调度器在分配 block 后， 再向 metaserver 反向登记 do_remote_decode=true 和 D 的 ZMQ 端点，Proxy 据此把同一个请求转发给 Prefill。 批量请求（如一次 OpenAI completion 展开成多个子请求）用 BATCH_KV_TRANSFER_PARAMS 携带每个子请求的参数。

代码结构：一个门面，四种组合

SfaRemoteD2HConnector 本身几乎不写业务逻辑，它按 进程角色（SCHEDULER / WORKER） × KV 角色（producer / consumer） 分派到四个实现类。理解这张矩阵，就理解了整个目录。

kv_producer（Prefill）
kv_consumer（Decode）
SCHEDULER
SFAPDRD2HProducerScheduler 记录本地 block；每步生成 SfaPDProducerMetadata，算 token 区间与 chunk_finish。
SFAPDRD2HScheduler 把 prompt 声明为外部 token；登记 main/indexer 目的地；分配 copy-sfa slot；HTTP 通知 metaserver。
WORKER
SFAPDRD2HProducerWorker MemFabric 注册 HBM；层钩子里记录事件并入队；复用闸门等待 D 读完。
SFAPDRD2HConsumerWorker 绑定 offload manager 的 CPU 池；启动读线程；聚合 TP 完成状态并回报调度器。

Decode 侧的关键三件事

  1. 声明外部 token：get_num_new_matched_tokens() 返回 prompt 长度与异步标志，让 vLLM 为整段 prompt 分配 block。
  2. 保留目的地：update_state_after_alloc() 把 main/indexer 两组的 block ids 存在本地，不发给 P。
  3. 反向登记：POST metaserver，只带 D 的 host/port/TP 尺寸与 do_remote_decode=true。

Prefill 侧的关键三件事

  1. 记录源 block：P 分配自己的 HBM block，只关心“我要暴露哪些源地址”。
  2. 逐层通知：每层 KV 写完（scatter 时或层末）把源 block 列表发给 D。
  3. 等回执再复用：物理 buffer 的复用被 READ_DONE 闸门卡住，避免 D 还在读就被覆盖。
为什么 D 不把 block id 发给 P？这是从 push 模型切到 pull 模型后刻意删掉的旧逻辑。P 若拿到 D 的目的地，就会退化成“P 决定写哪里”， 与 D 的 CPU 池所有权冲突；而 D 只需要按 req_id 在自己本地查表即可。
06

控制协议：四种消息，一条连接

控制面用 ZMQ：D 每个 TP rank 起一个 ROUTER，P 对每个 D 端点维护一个 DEALER。 消息用 msgspec.msgpack 编码，首元素是消息类型。

消息方向载荷要点作用
MF_METAP → D（每连接一次） P session id、每层 base_addrs / block_len / block_size_scale / group_idx / main_tensor_count / has_indexer、协议版本、PP rank/size 把 P 的源地址布局告诉 D；D 校验后回 MF_META_ACK（PP=1 的旧路径可回裸 ACK）
READ_READY_BATCHP → D（每层） 层号、层名、read_reqs=[(ext_id, main_ids, indexer_ids, main_start, indexer_start)]、done_ext_ids、group_member_idx、tp_ratio “这一层写好了，可以来读”；同一 D 端点的多个请求合并成一条
READ_DONED → P 层号 数据已落盘，P 可以释放该层的复用闸门
READ_FAILEDD → P 层号、错误字符串 P 记录到对应物理 slot，等待方抛错；D 同时把这些 block 标为无效

先把“源地址表”交出去：MF_META

每个 D 端点第一次收到数据前，P 会发一次 MF_META 并阻塞等待回执。它携带的是 P 的 MemFabric session id 与每层张量布局： 主 KV 固定 2 个张量（K、V），其后可选 indexer 张量与 LIC8 scale 张量。 

# send_thread.py：首次连接时的握手
dealer.send(encoder.encode(
    (MF_META, self._state.p_session, encoder.encode(p_meta_dict),
     SFAPD_PROTOCOL_VERSION, self._state.producer_pp_rank,
     self._state.producer_pp_size)))

每层一条：READ_READY_BATCH

dealer.send(encoder.encode(
    (READ_READY_BATCH, layer_idx, layer_name,
     read_reqs, done_ext_ids, group_member_idx, tp_ratio)))

P 会按 (remote_host, remote_port) 分组，把同一 D 端点的多个请求塞进同一条消息，减少 ZMQ 往返。 done_ext_ids 只在“最后一层 + 本 chunk 已算完”时出现，表示这个 chunk 的所有贡献者都可以报告完成了。

小细节：P 侧 update_decoder_info() 在 MemFabric 模式下直接返回原 meta，不发 GET_META。 因为 pull 模式下 P 根本不需要 D 的地址；省掉这轮请求可以避免占满 D 的 ROUTER 队列。

地址映射与 TP 切分：D 如何算出读哪里

描述符是三个等长数组：local_ptrs（D 地址）、peer_ptrs（P 地址）、lengths（字节数）。 构建过程就是一次“逻辑 block → 物理字节区间”的翻译。

Block 字节数怎么来

注册时对每个张量计算：

block_len        = tensor.element_size() * prod(tensor.shape[1:])
block_size_scale = tensor.shape[0] // num_blocks
外部 block 字节数 = block_len * block_size_scale

之所以有 scale，是为了兼容“外部 block 大小是 kernel block 整数倍”的布局： 一个 vLLM block 可能对应多个 kernel block 的存储。D 在读之前会用这个字节数与自己的池逐层比对， 主 KV、indexer、scale 任一项不匹配都会直接报错，而不是悄悄写坏数据。

P 地址 = p_base + p_block_id × (block_len × scale)　　D 地址 = d_base + d_block_id × 同尺寸

主 KV 的 TP 切分：每个 rank 只拉自己那段

D 的 CPU 池是 TP 共享的，但每个 TP rank 负责把主 KV 的一段拉进来。切分函数还会按 chunk 的全局起始 block 做旋转， 避免连续的小 chunk 总是落在 TP0： 

def _tp_block_range(num_blocks, tp_rank, tp_size, start_block=0):
    # 旋转首个 owner：连续小 chunk 不会全压到 TP0
    logical_rank = (tp_rank - start_block % tp_size) % tp_size
    blocks_per_rank, remainder = divmod(num_blocks, tp_size)
    start = logical_rank * blocks_per_rank + min(logical_rank, remainder)
    count = blocks_per_rank + int(logical_rank < remainder)
    return start, start + count

不等 TP：一个 D rank 由多个 P rank 共同喂

当 P_tp > D_tp 时，tp_ratio = P_tp // D_tp。一组 ratio 个 P rank 映射到同一个 D rank：

  • 主 KV：只由组内第 0 个贡献者（group_member_idx == 0）拉取，避免重复。
  • Indexer：每个 D rank 都需要完整一份，所以把 indexer block 再按 ratio 细分给各贡献者。
  • 完成判定：D 端累计 pp_size × ratio 个贡献者的末层到达，才算请求完成。
# worker.py：P rank 映射到 D TP rank
tp_ratio = prefill_tp_size // decode_tp_size
remote_tp_rank = prefill_tp_rank // tp_ratio
remote_port = base_port + remote_tp_rank   # D 每 rank 一个端口
端口不是随便加的：D 的基址用 全局 data_parallel_rank，不能用 data_parallel_rank_local。 否则单机多 DP 引擎的 local rank 都从 0 开始，会全部撞在 kv_port + 0。

描述符合并：把碎片区间拼成一次批量读

block 在物理上不一定连续。_coalesce_desc() 会同时检查 P 与 D 两侧地址是否连续， 把能接上的区间合并；两边的 block 顺序一致时，一整段 prompt 只需一个描述符。 

ret = self.engine.batch_transfer_sync_read(
    p_session, all_local_ptrs, all_peer_ptrs, all_lengths)
if ret != 0:
    raise RuntimeError(f"memfabric batch read failed, ret={ret}")

P 侧：两个钩子，一条队列

  • on_kv_cache_written()：scatter 完成即可提前派发，让 D 的拉取与后续 attention 重叠。
  • save_kv_layer()：层末兜底；若该层已在 scatter 时派发，则跳过（_pd_dispatched_layers）。
  • 两者都会 record_p_save_event() 记录 NPU event，发送线程在真正发消息前 synchronize()。
  • 任务入 send_queue，由 MembPullSendingThread 串行发送并按端点合并。

复用闸门按“物理 storage slot”计数

多个逻辑层可能共享同一块 NPU 地址，所以不能只用层号记账。Worker 在注册时从地址反推 layer_storage_slots，主 KV 与 indexer 分开成 slot： 

# 每个 slot 一个 Event，初始 set（首个占用者不阻塞）
storage_send_done_events[slot].set()

# 新一层写入前先 close 闸门
mark_layer_pending(layer_idx)

# READ_DONE 到达后才重新 set
_signal_layer_done(layer_idx)
为什么用“物理 slot”而不是“层”：Layerwise offload 会把 N 个逻辑层映射到 B 个物理 buffer。 L5 和 L9 可能写到同一块地址。若按层记账，L9 会以为 L5 的读已经结束；按 slot 记账才能覆盖“环形复用”的最后一圈。

Decode 完成判定：为什么要跨 TP 求交

主 KV 被切给多个 D TP rank，任何一个 rank 没读完，请求都不能算完成。因此每个 rank 维护自己的终态集合， 通过 CPU group 做 all_gather_object，取交集才是“所有 rank 都完成”；失败则取并集， 并把对应 main/indexer block 记为无效，交给 vLLM 重新计算。 

tp_status = self._gather_tp_read_status(set(self._terminal_ext_ids), local_failed)
finished_on_all = set.intersection(*(terminal for terminal, _ in tp_status))
failed_on_any = set().union(*(failed for _, failed in tp_status))

Copy-SFA 的两个小优化

Tail：只补最后一个不完整 block

prompt 末尾不足一个 block 时，读线程额外把这段 D2D 到该请求独占的 top-k 环形槽（两个 block 的环，按 block 号奇偶选偏移）， decode 首步不必再从 CPU 池 H2D。

Dense：短 prompt 整体放进热区

短请求直接把整个 prompt 的 block 复制到 top-k 行的 hot region，使 decode 可以在“非 offload”状态直接跑完， 完全省掉首次 H2D。两者的行号通过 get_prebound_copy_sfa_slots() 提前暴露给 model runner。

正确性不变量、失败路径与限制

四条必须成立的不变量

1. 布局三方一致

P 元数据、D 的 CPU 池、D 的 indexer/scale 张量，三者的 block 字节数必须相等；不一致在首次读之前就抛错。

2. 读毕才可覆写

物理 storage slot 的 Event 在发送前 clear，在 READ_DONE/READ_FAILED 后 set；首个占用者因初始为 set 而不阻塞。

3. 完成要全票通过

D 侧所有 TP rank 终态取交集；P 侧所有 PP × TP 贡献者到齐（pp_size × ratio）才算 chunk 完成。

4. chunk 边界按“已算 token”切

start_block = max(remote_cache_tokens, local_transed_tokens) / block_size； end_block 在 chunk 未完成时向下取整，完成时向上取整，保证不遗漏末尾半块。

失败时发生什么

  • D 读失败：回 READ_FAILED，P 把错误记到该层所有 slot，等待方抛 RuntimeError；D 把涉及的 block 标记为无效。
  • P 发送线程异常：清理所有 pending 层，置错误并释放闸门，避免死等。
  • metaserver 不可达：最多重试 3 次，失败后 1 秒定时器再投递；请求结束时取消 future/timer。
  • done 早于 request_map：外部 id 先挂在 _pending_done，后续每步重试映射，避免信号丢失。

已知限制

  • 传输后端只支持 MemFabric（pull 模式没有 push 写路径）。
  • Sparse Decode Offload 支持 DP + TP；CP / PP 不在支持范围（协议本身对 PP 有贡献者计数）。
  • Decode 必须开启 sparse_kv_offload_config，Prefill 必须关闭。
  • fused_copy_sfa 额外要求 index_topk=2048、block size 128、topk_buffer_size 为 256 的倍数等。
  • P 的 TP 必须 ≥ 且整除 D 的 TP。

一页总结

P 注册 HBM → 每层写完后发 READ_READY_BATCH → 等 READ_DONE 再复用物理 slot；
D 分配 main CPU + indexer HBM → 保留 block ids → 收到通知后按 TP 切分、合并描述符、 batch_transfer_sync_read → 聚合所有 TP/贡献者 → 告诉调度器“KV 就绪”。
本质 用控制面消息把“数据可见性”和“数据搬运”解耦，让拥有目的地的 Decode 掌握拉取节奏。
