01 OVERVIEW

定位与核心能力

HBM 容量有限，DRAM 带宽较低，跨节点访问需要额外的通信编程。MemFabric 将各 rank 的 HBM 与 DRAM 注册为逻辑连续、进程间视图一致的全局窗口，业务通过一个地址和一次拷贝调用完成访问， 无需感知数据所在节点与承载链路。

异构内存池化

每个 rank 注册本地 HBM 与 DRAM，按 rank 拼成对称窗口。BM 面向大容量池化，SHM 面向算子级共享，TRANS 面向已注册内存的点对点传输。

全局地址视图

GVA 起始地址与布局在所有进程中一致，按 rank 线性排布。地址本身包含归属信息：(gva − base) / maxSize 即远端 rank，无需索引表。

xcopy 内存语义接口

北向提供 smem_bm_copy / write / read，支持 L2G、G2L、G2H、H2G、G2G 以及批量与异步调用。方向判定与引擎选择由库内完成。

插件化数据传输

同一套接口支持 Device SDMA、Device RDMA/URMA/UBoE 与 Host RDMA/TCP/SHM。按可达性与 tag 策略排序，单个算子失败后自动尝试下一个。

控制面与数据面分离

Config Store 与 Group Manager 只负责成员管理、元数据交换和建链；数据搬运由单边读写完成，远端 CPU 不参与，也不设置中转缓冲区。

弹性与高可用

支持 autoRanking、动态 join/leave 与本地内存按需扩展。TCP 模式由 rank0 兼任 Store；etcd 模式基于租约选主，leader 变更可回调上层。

GVAGlobal Virtual Address，全局统一虚拟地址 BMBig Memory，大容量池化语义 LLocal（本机 HBM/DRAM） GGlobal（全局窗口） RHRemote Host，跨机 DRAM D2RH本机 HBM → 跨机 DRAM RH2D跨机 DRAM → 本机 HBM one-sided单边读写，远端 CPU 不参与
02 CODE MAP

代码结构

仓库按语义层、核心层、控制面与应用划分。src/smem 生成 libmf_smem.so，src/hybm 生成 libmf_hybm_core.so， Offload 与 acc_links 各自成库；控制面同时提供进程内 TCP Store 与可选 etcd 后端。上方结构图给出层次与调用方向， 下方按模块展开，点击左侧模块查看职责与入口文件。

全局代码结构与调用关系 上层只调用下层的公开接口；跨层直调只有两处：smem → hybm、acc_offload → hybm host API。悬停模块查看职责，点击跳转模块详情。

语义层与核心层

smem_bm 管理池化与 GVA 拷贝，smem_trans 处理已注册内存的点对点传输， smem_shm 提供同机算子共享。三者复用 hybm 的地址、建链与算子。

南向扩展点

新增链路需实现 TransportManager（信息交换、连接、可达性）与 DataOperator（按描述符搬运）。上层按优先级与 tag 选择，不感知具体协议。

控制面实现

Config Store 抽象 KV、Watch、CAS 与选主能力。TCP 模式无外部依赖，rank0 兼任服务端；etcd 模式提供租约与 HA， 通过 Go 共享库接入。

Exchange Info 的内容

Entity 级信息包含 rankId、NIC 地址与传输私有数据（QP / URMA 信息）；Slice 级信息包含 GVA、大小与传输内存键。 两者经 Config Store 的 KV 与 Group Manager 广播到相关 rank。

Import 与 mmap

导入交换信息后，hybm 在各内存段登记 GVA 到对端窗口的映射，并调用 HAL 完成地址映射；随后按 rank 建立传输连接。 映射完成后，对端 GVA 可直接参与本进程寻址。

PROMOTE_TO_ACTIVE 的作用

join 并非登记即返回。服务端需将链路推进至 CONNECTED 后才把 rank 置为 ACTIVE， 因此 join 返回时数据面已可用。

05 STATE MACHINE

组网状态机

Group Manager 维护两类状态：rank 生命周期（IDLE → CHECKED_IN → ACTIVE）与有向链路状态 （IDLE → EXCHANGING → EXCHANGED → CONNECTING → CONNECTED）。服务端推进状态，客户端通过回调执行导入、映射与建链。

server 侧：CheckIn / Checkout / ResetRankState
IDLE → CHECKED_IN → ACTIVE
IDLE：不在组内；CHECKED_IN：信息已登记、尚未接受连接；ACTIVE：在线可访问。Checkout 或断链会回到 IDLE。

08 ACC OFFLOAD

KV Cache 卸载

LLM 推理的 KV Cache 由大量不连续的 block 组成。Offload 从预留的 DRAM 池分配内存，通过卡侧稀疏拷贝算子 将多个离散源地址一次搬运到多个离散目的地址，支持 LOCAL 与 SHARED 两种池化方式。

接口与执行方式

接口接收源地址数组、目的地址数组、长度数组与任务数，在 device 上异步执行；Python 侧提供 empty 与 sparse_copy 封装。

// C 接口：地址数组 + 长度数组 + 任务数
int32_t offload_sparse_copy(
    uint64_t srcPtr, uint64_t dstPtr,
    uint64_t lenPtr, uint64_t sizePtr,
    uint16_t deviceId);
LOCAL每 rank 独占一份本地 DRAM 池，reserveSize 与 allocSize 相等。
SHARED多 rank 共享同一份 DRAM 池，通过 storeUrl 汇聚；按需扩容，适合集中式 KV Cache 池。
使用稀疏拷贝的原因：单个 KV block 通常由 61 段 128 KB 与 61 段 16 KB 组成（约 8.57 MB，122 个离散地址）。 逐段调用 DMA 时启动开销占比过高；稀疏拷贝将地址数组与长度数组一次下发，由卡侧算子并发执行。

稀疏拷贝的实现

逐段调用：N 次拷贝

  • 每个离散段一次 host 调用与一次 stream 任务，122 段即 122 次下发。
  • 单段 16 KB 时，固定启动开销远大于有效数据量，带宽利用率低。
  • 段间没有跨调用的流水；若要并行，需应用自行拆分并管理多条 stream。
  • 地址与长度由 host 逐次传入，每次都经过参数校验与任务下发。

单次稀疏拷贝

  • 一次调用下发源地址数组、目的地址数组、长度数组与任务数，只产生一个 stream 任务。
  • 数组与任务数驻留 device 内存，kernel 直接读取，不需要 host 回读或逐段下发。
  • 搬运由卡侧多核并行完成，host 不再逐段驱动，也不再受单段启动开销拖累。
  • 段与段之间不要求连续、等长或同序，源和目的可各自独立寻址。
两条泳道搬运相同的 6 个离散段，共用同一时间轴；每格为 1 个示意时间窗。

底层调用链路：host → ACL → AIV

一次 sparse_copy 只产生一次算子下发。host 侧解析四个 device 指针并把它挂到调用方的 ACL stream；任务数、地址数组与长度数组始终留在 device 内存，由 AIV 核自行读取、切分与搬运。

ACL 与 Launch 的关键约束

  • 复用调用方 stream：与前后 torch_npu 算子同流保序，库内不建流、不做同步。
  • blockDim 固定为 AIV 核数（A3 48 / A5 64）：无论多少段，只占一个 launch 槽位。
  • 接口只传 4 个 device 指针：任务数由 kernel 从 device 内存读取，host 不传标量，图捕获回放时无需重算参数。
  • 算子包与主库解耦：A3 / A5 分别构建，符号缺失只降级该接口。
  • 返回即入队完成：等待由调用方 stream 同步或后续算子依赖保证。

AIV 核内的两条分支

  • size ≥ 核数：前 size/2 组为 K、其余为 V；核 i 从组 i 开始，每次加核数取下一组。
  • 该分支使用深度 2 的 TQueBind(VECIN→VECOUT)，每块 88 KB：下一组 CopyIn 与当前组 CopyOut 重叠。
  • size < 核数：总字节按核数均分，余数给前几个核；每核只处理与自己区间相交的段。
  • 该分支单缓冲深度 1、176 KB，按 176 KB 分块循环，适用于段少而单段大的场景。
  • 两条分支都用 DataCopyPad 处理任意字节长度，段间无需连续、等长或同序。
