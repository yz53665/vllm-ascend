DSA 原理动图
DeepSeek Sparse Attention

传统 attention 每生成一个 token，都要把 L 个历史 token 的 KV 全部搬进计算单元。 DSA 换了个顺序：先用一份很轻的索引把 L 扫一遍，选出 k 个位置， 再只搬这 k 份 KV。下面的动图把“扫、选、搬、算”拆成逐块可见的动作。

01

一页看懂：DSA 只是把“全量”换成了“先选再算”

三个动作，对应三份不同的数据，字节数差一个数量级。

1 · 扫 轻量索引

每个历史 token 额外存一份 128 维 int8 的 indexer K（约 128 B/token）， 用 64 个 128 维小 head 与当前 query 做点积，得到 L 个分数。读的是细索引，不是主 KV。

主 KV：576 维 bf16 = 1152 B/token

2 · 选 每个 query 独立 Top-k

对当前 query 的 L 个分数取前 k 个 token 位置。DSV3.2 默认 2048， GLM 类模型常见 512；k 由 index_topk 配置。

索引是 token 级，不是整页

3 · 算 稀疏 attention

Q 只与这 k 个位置的 KV 做 softmax 和加权求和。主 attention 的 QK 对数从 L 降到 k，KV 读取也从 L 行降到 k 行。

sparse_block_size = 1

scoret,i = Σh=1..64 wh · ( qth · kih )   →   It = TopK( scoret , k )
ot = softmax( qt · K[It]T / √d ) · V[It]   // 只在 k 个位置上做 softmax
KV 读取： L × 1152 B  →  L × 128 B  +  k × 1152 B
读图约定：页面里每个方块是一页 KV，固定 128 个 token；粗条是主 KV（576 维 bf16）， 细条是 indexer K（128 维 int8）。为了看清动作，动图把字节数缩小成“页”为单位； 第 6 章会用真实长度算账。所有数字都是“单层、单 query”的量级。

传统：每页都要开

16 页全部进入计算单元，单页主 KV 128 × 1152 B = 144 KB， 合计 2.25 MB。没有“选”的动作，也就没有额外索引开销。

DSA：先付一笔小钱

16 条 indexer K 共 16 × 16 KB = 256 KB，然后只搬 4 页 = 576 KB，合计 0.81 MB，是传统路线的 36%。

真实场景里 k 更小

玩具示例 top-k 占 25%，真实 k / L 往往只有 1.6%–6.3%， DSA 省下的主 KV 搬运更多；但索引全扫的 11% 是固定底噪。

块级寻址：一条稀疏索引如何落到一行 KV

索引给的是 token 位置；kernel 要先查 block_table，再在页内按偏移取行。

逻辑 token 序列

命中的 token 919 落在逻辑页 7（token 896–1023）

block_table

logical page → physical page

物理页 P21 · 128 行

row 0row 63row 127

偏移 = token % 128；命中 row 3 / 57 / 100

gather buffer

空

只装被选中的行，供 attention kernel 使用

步骤 1 / 4

logical → physical

paged KV 不保证逻辑页连续。稀疏索引指向逻辑 token， kernel 用 block_table[token // 128] 换算出物理页号。

页内偏移

row = token % 128。同一页里只有 3 行被命中， 其余 125 行不需要进入计算单元。

搬运粒度

sparse_block_size = 1 表示按 token 行 gather。 逻辑字节是 k 行；实际带宽会受随机访问、cache line 与 DRAM 行局部性影响。

05

本仓库里的三种 DSA 形态

同一条主线，差别在“索引作用在谁身上”以及“是否先把 KV 压缩”。

compress_ratio ≤ 1

纯滑窗：不做 top-k

t-7t-6t-5 t-4t-3t-2 t-1qt
  • attention 直接看最近 sliding_window 个 token
  • ori_mask_mode=4，ori_win_left=window-1
  • 没有 indexer 扫描，也没有稀疏索引

compress_ratio = 4

SWA + 4:1 压缩 + top-k

t0t1t2t3 →c0 · · ·c1
  • compressor 每 4 个 token 生成 1 条 compressed KV，带 2× overlap
  • indexer 在压缩 KV 上选 top-k，cmp_sparse_indices + cmp_ratio=4
  • 同时保留 SWA 分支（ori_kv），两条分支在一次 attention 内合并

compress_ratio = 128

SWA + 128:1 压缩，不做 top-k

t0t1…t127 →c0
  • compressor 每 128 个 token 生成 1 条 compressed KV
  • 压缩后序列已经很短，直接全量看 compressed KV
  • 省掉 indexer，但压缩 KV 的表达是近似

IndexCache：跨层复用 top-k

首层算一次，后面几层直接读 buffer

L0 · F L1 · S L2 · S L3 · F L4 · S
  • skip_topk=True 的层不再跑 indexer，直接读 topk_indices_buffer
  • 层间模式来自 index_topk_pattern（F=算，S=复用）与 index_topk_freq
  • 省的是 indexer 计算与细条读取，代价是假设相邻层 top-k 足够相似

索引与 KV 的量化

让“扫一遍”的固定成本尽量小

  • indexer K 用 int8（A5 上为 fp8_e4m3），每 token 128 B
  • query 也可量化：npu_lightning_indexer_quant 带 query/key 的 dequant scale
  • C8 路径下主 KV 打包成量化格式，走 npu_kv_quant_sparse_flash_attention
  • 索引越小，L 很大时的“底噪”越低，但打分精度也越依赖校准

省的是“主 KV”，不是全部

DSA 仍需把 L 条 indexer K 全扫一遍，这部分约为主 KV 字节的 128 / 1152 = 11.1%。它不随 k 变小而消失。

短上下文会倒亏

当 L × 128 + k × 1152 > L × 1152，即 L < k × 1152 / 1024 ≈ 2304 时，DSA 读得比传统还多。 稀疏注意力是长上下文方案。

计算降得比带宽多

主 attention 的 QK 对数从 L 降到 k，L=32k 时只剩 6.3%； 但 KV 带宽只降到 17.4%。所以 DSA 的收益更多体现在算力侧。

08

代价与边界：动图没画出来的部分

DSA 不是免费的近似，它把成本从“主 attention”搬到了“索引”和“随机访问”。

01 Indexer 仍是 O(L)

全量扫描没有消失，只是每次只读 128 B 而不是 1152 B。L 越大，这 11% 的绝对字节也越大； 短上下文会被它拖成负收益。

02 近似精度

top-k 丢掉的位置不会回补。k 越小越快，但越依赖 indexer 打分与真实 attention 的相关性； k 的取值是精度与成本的直接旋钮。

03 随机访问的有效带宽

逻辑上只搬 k 行，但行地址分散会降低 DRAM 行局部性与 L2 命中率。 实测收益通常小于“字节比”算出来的理论上限。

04 索引也要存

每 token 每层多 128 B 的 indexer K，约为 MLA 主 KV 的 11%。 长上下文下这是一笔可观的常驻显存，需要和 KV 池一起规划。

05 压缩是另一层近似

c=4 时 top-k 命中的是“4 token 合 1”的压缩条目，c=128 时是“128 合 1”。 省得更多，但 compressed KV 无法还原细粒度信息，所以还要叠加 SWA 保住近处。

06 层间复用是假设

IndexCache 让后续层直接复用首层 top-k，省掉重复扫描； 一旦相邻层关注的位置差异大，精度会掉，因此需要 F/S 模式逐层配置。

一句话总结：DSA 把“每个 query 看全部 L 个 token”改成“先用 1/9 的字节扫一遍， 选 k 个，再看这 k 个”。计算量按 k/L 下降，带宽按 (L×128 + k×1152)/(L×1152) 下降； 代价是索引常驻显存、随机访问效率，以及 top-k 的近似误差。
